# Design: Per-robot containers (`.robocode`)

> Status: **Implemented** (26.9.2) — see `CHANGELOG.md` and `docs/ROADMAP.md` Phase 4

## Problem

The extension currently infers which robot a program belongs to by checking whether it sits
inside a folder containing `.va` controller data files. This breaks down when:

- **Workspaces use structured directories** — working programs (`.ls`, `.kl`) are in one place,
  archived backups in another, and a single workspace covers multiple robots
- **Backups are versioned archives** — the extension indexes them as editable programs, polluting
  the tree and inviting accidental edits
- **Multi-robot cells** need each working directory scoped to a specific robot's controller data
  (register comments, frames, macros), but working files don't sit inside the `.va` folder

Any fix that encodes a directory convention (e.g. `robotFolders: [{folder, dataFolder}]`) inherits
the fragility of that convention. The correct design makes the relationship **explicit and
self-describing**.

## Proposal: `.robocode` containers

Two kinds of hidden directories, discovered by scanning:

```
cell/                                  # workspace / git root
  .robocode-cell/
    cell.json                          # optional anchor: cell name + future conventions
  robot 1/
    .robocode-robot/
      robot.json                       # authored declaration
      snapshot.json                    # generated provenance
      .gitignore                       # auto-written: "snapshot/"
      snapshot/                        # verbatim full robot backup
        numreg.va, *.ls, *.tp, *.kl, *.pc …
    LS/  KL/                           # working programs — the only editable set
    backups/                           # versioned archives — never touched
```

## Files

### `.robocode-cell/cell.json`

Optional. Gives the extension a known anchor at the workspace root. Holds cell-level
metadata now; conventions, header templates, and other workspace-wide settings later.

```json
{
  "name": "Paint Cell 4",
  "controllers": {
    "S002R01": {
      "host": "192.168.1.100",
      "device": "MD:"
    },
    "S002R02": {
      "host": "192.168.1.101",
      "useFtp": true,
      "ftpPort": 21
    }
  }
}
```

| Field | Required | Notes |
|-------|----------|-------|
| `name` | no | Cell label shown in views. |
| `controllers` | no | Map of controller names to connection details. Each key is a controller name that `robot.json` can reference. Connection fields: `host` (required), `httpPort` (default 80), `ftpPort` (default 21), `ftpUser` (default ""), `device` (default "MD:"), `useFtp` (default false), `autoConnect` (default false), `autoRefresh` (default false), `pollIntervalMs` (default 5000). Passwords are never stored here — they stay in VS Code SecretStorage. |

**Cell containers are optional.** Robot containers work standalone anywhere — the scan
discovers them regardless. A cell container simply adds a name and a future-proof home for
configurables. When controllers are defined in cell.json, they are auto-registered as
robot profiles on workspace load, taking precedence over `robotCode.robots` settings for
the same controller name.

### `.robocode-robot/robot.json`

Required. Declares this folder as one robot's working area.

```json
{
  "name": "S002R01",
  "programs": ["LS", "KL"],
  "exclude": ["backups"],
  "controller": "S002R01"
}
```

| Field | Required | Default | Notes |
|-------|----------|---------|-------|
| `name` | no | folder name | Robot label shown in views, status bar. Matches live robot profile names for the connection UI. |
| `programs` | no | all subdirs + root files except `.robocode-robot/` and `exclude` | Relative to the robot folder. These are the working directories the extension indexes as editable programs. |
| `exclude` | no | `[]` | Only used when `programs` is omitted. Folders to skip. |
| `controller` | no | — | Name of a controller defined in the cell's `cell.json` controllers map. Binds this robot container to a specific controller for live connections and snapshot-from-robot. |

### `.robocode-robot/snapshot.json`

Generated by the extension. Records provenance of the current snapshot — when it was
created, where from, what it contains.

```json
{
  "date": "2026-09-18T14:30:00Z",
  "source": {
    "kind": "backup",
    "path": "../backups/S002R01_260915"
  },
  "fileCount": 247,
  "controller": {
    "name": "S002R01",
    "version": "V9.40",
    "fNumber": "F368808"
  }
}
```

`source.kind` is `"backup"` (folder copy) or `"robot"` (FTP/HTTP pull). Controller info
populated when available from `parseControllerInfo`.

### `.robocode-robot/snapshot/`

A complete, verbatim robot backup — all `.va` data files, all programs (`.ls`, `.tp`, `.kl`,
`.pc`), everything. Created by the snapshot commands. Wholesale-replaced on re-snapshot.

This directory qualifies as a **dataset** under the existing DataStore rules (a folder
containing `.va` files), so minimal new code is needed to route working files to it.

### `.robocode-robot/.gitignore`

Auto-written by the init wizard. Contains `snapshot/` — a full backup is tens of MB of
regenerable data. Delete this file to opt into committing snapshots.

Controlled by the setting `robotCode.containers.gitignoreSnapshot` (default `true`).

## Behavior

### Marker discovery

- **Scan** `findFiles('**/.robocode-robot/robot.json')` at workspace refresh + watcher events
- **Cell** `findFiles('**/.robocode-cell/cell.json')` at each workspace folder root
- Parse errors → warning in Output channel, robot folder falls back to default behavior
- Watcher events for markers under `files.watcherExclude` may be missed — full refresh
  via command mitigates (same known limitation as existing file watchers)

### Partitioning

When robot markers exist in the workspace, **only declared folders are indexed**:

| Path | Indexed as | Source |
|------|-----------|--------|
| Working folders (`LS/`, `KL/`…) | Working programs | Editable, shown in tree, full language features |
| `snapshot/**` | Reference programs | Resolve CALLs/callers/xref; hidden from tree; never edited |
| `backups/`, `.robot-history/`, `exclude` entries | **Invisible** | Not indexed, not scanned for `.va` |
| `.robocode-robot/` config (robot.json etc.) | Excluded | Not indexed |
| `.robocode-cell/**` | Excluded | Not indexed |
| Folders NOT under any robot marker | Default today | Same as current behavior — index everything, containment-based grouping |

**Incremental adoption**: a workspace can mix robot folders with un-marked folders. Marked
folders are partitioned; un-marked folders keep today's behavior.

### Grouping

One **group** per robot folder. Every working program and reference program under a robot
folder share the same group key (the robot folder path, lowercased). This means:

- CALL resolution scopes per robot
- Register/I-O comment mismatch is per-robot
- Cross-reference findings are per-robot
- "Missing CALL target" only fires for calls that don't exist in the same robot's snapshot

### Data association

The robot folder's `snapshot/` directory is the **single dataset** for that robot. Working
programs get register comments, frames, macros, payloads, and system variables from the
snapshot's `.va` files — no date heuristics, no newest-wins, no ambiguity.

All datasets (one per robot) appear in the Backup view with the robot name, snapshot date,
and source.

### Reference indexing

Snapshot `.ls`/`.tp`/`.kl`/`.pc` files are indexed with `reference: true` on `ProgramInfo`:

- **Resolve** CALLs, callers, cross-reference — no false "missing CALL target" diagnostics
- **Hidden** from the TP/PC program tree — no clickable, editable rows
- **Preferred ranking**: when both a working copy and a snapshot copy exist for the same
  name, the working copy wins in `get()` resolution, tree display, and consumers
- **Re-number/Format Document** targets only working programs (not reference)

### Modified-vs-snapshot marker

Every working program is compared against its same-name copy in `snapshot/`:

| Status | Display | Action |
|--------|---------|--------|
| Identical | `= snapshot 2026-09-15` | None |
| Differs | `≠ snapshot · N lines differ` | Click → `vscode.diff` (working ↔ snapshot) |
| No snapshot copy | `not in snapshot` | — |

Comparison: normalized text compare (`\r\n` → `\n`, trailing whitespace). Computed at
index time (hash of normalized text stored on `ProgramInfo`, invalidated by watcher events).

Snapshot-only programs are surfaced as a count in the Backup view row:
"14 on robot, not in working folders" — visibility without tree pollution.

### Backup view

Per-robot rows replace today's per-dataset rows (when markers are present):

| Robot | Snapshot | Programs | Status |
|-------|----------|----------|--------|
| S002R01 | 2026-09-15 · from backup | 247 | Re-snapshot… |
| S002R02 | No snapshot yet | — | Snapshot from… |

The "Re-snapshot" buttons open the same wizard as the init (reuse the snapshot commands).

## New commands

| Command | ID | Description |
|---------|----|-------------|
| Initialize Cell… | `robotCode.containers.initCell` | Create `.robocode-cell/cell.json` at the workspace root, optionally add controller definitions |
| Initialize Robot Container… | `robotCode.containers.initRobot` | Wizard: pick folder → name → program folders → controller binding → gitignore choice → first snapshot |
| Snapshot from Backup… | `robotCode.data.snapshotFromBackup` | Pick a backup folder, recursive wholesale copy into `snapshot/` |
| Snapshot from Robot… | `robotCode.data.snapshotFromRobot` | Reuse FTP/HTTP backup-download machinery, pull into `snapshot/` (prefers controller binding from robot.json) |

## New setting

| Setting | Default | Notes |
|---------|---------|-------|
| `robotCode.containers.gitignoreSnapshot` | `true` | Auto-write `snapshot/` in `.robocode-robot/.gitignore` on init |

## Implementation

### Step 1 — Pure module: `packages/core/src/robotContainers.ts`

**vscode-free** (so `test/run.ts` can import it). Contains:

- `robot.json` / `cell.json` parse + validate (including `controller` field and `controllers` map)
- `CellControllerSpec` type for cell.json controller definitions
- `partitionClassify(uri, markers)` → `'working' | 'reference' | 'excluded' | 'unmanaged'`
- `robotFolderOf(uri, markers)` → the matching robot container, or undefined
- `snapshotProvenance` type (for `snapshot.json`)
- Overlap detection (nested or duplicate markers → first wins + warning)

### Step 2 — WorkspaceIndex: discovery + partition

- `findFiles('**/.robocode-robot/robot.json')` + watcher on the same pattern
- `findFiles('**/.robocode-cell/cell.json')` at workspace roots
- Partition filter: reference-flag `ProgramInfo` entries under `snapshot/`; exclude all others
  in marked robot folders
- Ranking tweak: `get()` prefers non-reference copies
- Audit all `ProgramInfo` consumers: trees, callGraph, rename, commentSync, xref tools

### Step 3 — DataStore: dataset routing

- `dataset(uri)` first asks `robotFolderOf()`; if matched, routes to `snapshot/`
- `.va` scan partitioned: don't create datasets from `backups/` under robot folders
- Multiple robot containers → multiple datasets (one per robot), disambiguated by robot name

### Step 4 — Services: resolvers

- `groupResolver`: robot folder path = group key
- `backupResolver`: snapshot dir = backup root

### Step 5 — Commands + package.json

- Four commands (init cell, init robot, snapshot from backup, snapshot from robot)
- `robotCode.containers.gitignoreSnapshot` setting
- Commands: `robotCode.containers.initCell`, `robotCode.containers.initRobot`,
  `robotCode.data.snapshotFromBackup`, `robotCode.data.snapshotFromRobot`

### Step 6 — Trees

- Backup view per-robot snapshot rows
- Working-row `=/≠/not in` statuses + diff command
- Reference rows filtered from TP/PC program trees
- Snapshot-only count badge

### Step 7 — Debug launch

Second `.vscode/launch.json` config with a placeholder path:
```json
{
  "name": "Run Extension (cell workspace)",
  "type": "extensionHost",
  "request": "launch",
  "args": [
    "--extensionDevelopmentPath=${workspaceFolder}",
    "<PATH-TO-YOUR-CELL>"
  ],
  "outFiles": ["${workspaceFolder}/dist/**/*.js"],
  "preLaunchTask": "npm: build"
}
```

### Step 8 — Tests

- `test/fixtures-cell/` — minimal two-robot tree:
  - `robotA/.robocode-robot/robot.json`, `snapshot/numreg.va`, `snapshot/prog.ls`, `LS/prog.ls`
  - `robotA/backups/` (decoy)
  - `robotB/` with marker, no snapshot
  - `.robocode-cell/cell.json`
- `test/run.ts` — pure-module checks (via `robotContainers.ts`):
  - Parse/validate robot.json, cell.json
  - Partition classification for working/reference/excluded/unmanaged paths
  - Overlap/warning logic
  - Marker resolution
- Snapshot provenance parsing (round-trip through `snapshot.json`)
- Modified-marker hash/status (same/modified/not-in-snapshot)
- `run.ts` already does not import vscode — the pure module fits this pattern

## Out of scope

- Rebranding (`.robocode` is just the container name; extension stays "Robot Code")
- Generic exclude setting (partition handles this)
- Cell-level conventions beyond `name` and `controllers` (designed for, added later)
- Live-tier changes beyond snapshot-from-robot (the pull reuses existing machinery)
- Other robot brands (same architecture allows adding module folders under `src/`)

## Edge cases

- **Overlapping markers** (nested robot folders): first marker wins, warning in Output
- **Missing folders**: warning, skipped
- **Malformed robot.json**: warning, folder falls back to default behavior
- **Cell container absent**: robot markers work standalone; cell is optional
- **Workspace without markers**: unchanged — `backupFolders` setting + containment grouping
- **Windows case-insensitivity**: group keys already lowercased
- **Multi-root workspaces**: scan each workspace folder root for both marker kinds
- **Watcher events dropped** (under `files.watcherExclude`): full refresh command mitigates
